## Issues fixed

1. **Faint selected-page numbers.** The original 11px sidebar number colour `#7e6b52` had measured contrast of 3.91:1 against the selected-page background. Page numbers now use the shared, darker muted-text token and are checked on the populated desktop sheet.
2. **Cramped sign-in fields on phones.** Mobile email/password inputs now use at least 44px height and 16px text. The placeholder opacity is increased from 50% to 85% and follows the on-primary colour. Keyboard focus gets an explicit visible accent outline.
3. **Colour changes stopping at component boundaries.** Common brand colours now flow through one token stylesheet, the existing `--ui-*` aliases and the sheet’s `--vault-*` aliases. Shared dialogs and the Adobe controls inherit the same palette instead of remaining burgundy when the surrounding page changes.
4. **Dependency gaps on standalone public pages.** The legal and 404 pages load the palette before their component stylesheet, just as the main page does. They receive their own responsive/browser checks.
5. **Poor discovery of mobile paper zoom.** A short mobile instruction explains how to enlarge paper fields and move around the enlarged page. It disappears in print. This helps the current fixed-paper design; it does not turn it into a reflowing mobile form.

6. **Enter did not submit email sign-in.** The header’s controls were a `div` with click-only handlers. They are now an accessible form with one submit handler, shared credential validation for sign-in/registration, readable validation feedback and a **Sign in** button. The test verifies exactly one provider call per Enter/button submission and none for invalid credentials; the provider is a stub, so no real sign-in/registration is performed.

7. **Nested 404 pages lost their styling and home link.** At a missing URL such as `/missing/nested/page`, relative asset/link URLs resolved into that missing directory. The 404 page now uses root-relative styles, home and legal links. A dedicated browser case simulates Hosting’s nested 404 response and verifies both styling and return navigation.

The default remains the existing light parchment/burgundy/gold design, with some low-contrast captions darkened and near-identical heading colours unified. The changes affect presentation and form interaction: no game-rule data, source metadata, storage format, ownership, equipment calculations or Firebase rules changed.

## Copy and spelling review

Visible public/interface text and instructions captured by the review were checked against a local English Hunspell dictionary and the exceptions were reviewed manually. British spellings such as *catalogue*, *licence* and *labelled*, D&D terms, abbreviations, proper names and synthetic character names were retained. No clear spelling error was found in the captured interface copy. The mobile zoom instruction and password-reset follow-up were rewritten for clarity, and the email action uses the verb **Sign in**.

This is a review of the captured interface copy, not a proofread of every book entry, all catalogue combinations or real players’ campaign text. Source names, legal attribution and player-authored content are not automatically “corrected.” Captured text is included in `review.json` so future copy reviews can use the same evidence.

## Remaining mobile-paper limitation

**The source PDF layout at Fit width has many undersized targets on a phone.** The review records these findings separately under `paperTargetSize` in `review.json`. They are not silently counted as passing WCAG 2.2. The surrounding controls and native editing dialogs pass their target-size checks; original paper fields are included in the WCAG 2.0/2.1 checks but excluded from that separate surrounding-UI target-size assertion.

Zoom enlarges ordinary text-field targets and permits internal horizontal scrolling; native dialogs provide larger controls for their supported workflows. A comprehensive solution needs a separate mobile entry/reflow design with complete field access. Increasing every absolute-positioned PDF field to 24–44px would overlap neighbouring controls and damage the original layout. This remains a high-priority UI follow-up, rather than a claim that all source-paper controls are touch-accessible at Fit width.

## Colour preference extension

`css/theme-tokens.css` is the shared API. It is loaded before component styles on all three public HTML entry points. Screen components reference semantic tokens, including the aliases already used by legacy shared editors. The original PDF art, semantic error/success/rarity colours and game data are independent of the main brand palette.

| Purpose | Tokens |
| --- | --- |
| Main actions and headings | `--theme-primary`, `--theme-primary-hover`, `--theme-heading`, `--theme-on-primary` |
| Accent/decorative colour and readable accent text | `--theme-accent`, `--theme-accent-deep`, `--theme-accent-ink` |
| Canvas and header | `--theme-canvas`, `--theme-canvas-end`, `--theme-header`, `--theme-header-end` |
| Light surfaces | `--theme-paper`, `--theme-paper-soft`, `--theme-parchment` |
| Text, boundaries and focus | `--theme-ink`, `--theme-muted`, `--theme-border`, `--theme-border-soft`, `--theme-focus` |

For example, an eventual preference initializer can set a main colour and its companion shades on `<html>`:

```js
const root = document.documentElement.style;
root.setProperty('--theme-primary', '#1d5b44');
root.setProperty('--theme-primary-hover', '#143f30');
root.setProperty('--theme-heading', '#164735');
root.setProperty('--theme-accent', '#d8bd75');
root.setProperty('--theme-accent-ink', '#6f5014');
```

The three complete QA palettes are in `tests/site-palette-browser.cjs`; they are not offered as player settings yet. Component-specific neutral shades may remain warm, and the source paper stays white. These are light-palette tests, not a dark-mode implementation or proof that any arbitrary user-selected colour will be readable.

A future player preference UI should validate colour values and all contrast pairs, offer a preview with Apply/Cancel/Reset, save the palette separately from character mechanics, apply it consistently on account changes/reload, and update browser theme-colour metadata when appropriate. This task adds the stylesheet foundation and regression matrix; account preference controls/persistence remain a separate feature.

```bash

node scripts/test-profiles.cjs run browser -- playwright install --with-deps chromium
node scripts/test-profiles.cjs run browser -- npm --prefix tests run test:ui-palette
node scripts/test-profiles.cjs run browser -- npm --prefix tests run test:ui-consistency
node scripts/test-profiles.cjs run browser -- npm --prefix tests run test:ui
node scripts/test-profiles.cjs run core,browser -- npm --prefix tests test
```

PDF checks also require `pdftotext` (Poppler). CI installs it. Live Google sign-in, real email deliverability and physical Safari/Firefox/touch-device behaviour require their own integration/device checks; this Chromium fixture run does not establish those outcomes. Existing Firestore/Storage emulator and full application/browser/Adobe regressions remain required alongside the new palette job.
